# .code-style.md — Turbofa Kotlin Code Style

The single source of truth for code style in the turbofa project (Kotlin, Ktor, Koog).
Every agent that writes code follows these rules; code-style-reviewer enforces them
mechanically via ktlint + detekt.

## Formatting

- Indentation (4 spaces), max line length (120), charset, EOL and final newline are
  machine-enforced via .editorconfig (ktlint reads it)
- Trailing commas in multi-line declarations and call sites
- Single quotes where Kotlin allows them: char literals ('a'); string literals always
  use double quotes ("text") — a Kotlin language requirement

## Naming

- camelCase: functions, variables, parameters
- PascalCase: classes, interfaces, objects, enums
- UPPER_SNAKE_CASE: constants (const val, top-level val)

## Imports

- No wildcard imports
- Alphabetically sorted within each group
- Grouping order: java.*, kotlin.*, third-party, project (com.eduai.*) — blank line
  between groups

## Kotlin specifics

- DTOs as data class
- Hierarchies as sealed class / sealed interface
- Extension functions preferred over util classes

## Error handling

- Result<T> or explicit exceptions
- Never swallow errors (no empty catch blocks)

## Security

- DB credentials (DB_URL, DB_USER, DB_PASSWORD) are never passed to AI APIs (D11)
- RequestLogger masks secrets (DB_PASSWORD, DEEPSEEK_API_KEY, Authorization)
- .env is never committed to git
- DDL scripts (docs/schema.sql) are the only way to show DB structure to the AI

## DB

- Exposed ORM for the query layer (Tables.kt + transaction { }), HikariCP for connection
  pooling (three pools, D7)
- Table objects are structure-only (docs/schema.sql); SchemaUtils.create never runs in
  main code — SELECT only (R5)
- ktlint's function-signature rule is disabled in .editorconfig: it conflicts with the
  Exposed/Ktor DSL chain idiom

## Multi-model routing

- Provider per request via the Bruno DTO: default DEEPSEEK (external API), OLLAMA for
  local inference; the routing decision lives in ChatService (D12), never in the LLM
- Both providers share the same tool set, system prompt and history contract — only
  the transport differs

## DI

- Kodein DI via di/AppModule.kt (T22): modules config/db/client/logging/service,
  every dependency via bind<T>() with singleton { }. Application.module() builds the
  context and resolves with `by di.instance<T>()` — no manual wiring, no global
  service locators or singletons scattered across modules.

## Comments

- Minimal comments: only for non-trivial business logic that cannot be expressed via
  function names; external contracts (APIs, protocols); workarounds for known library
  bugs/limitations; or Decision log references (D1, D4, ...) on the code that
  implements those decisions
- Variable/function names must be self-documenting; if a function needs a comment to
  be understood — rename or decompose it
- If a function/class/module is understandable without the comment, the comment must
  be deleted
- FORBIDDEN: KDoc on trivial objects/classes with a single function (e.g. an object
  Helper with a single init() function); comments before self-evident modules/functions
  ("Env configuration", "Read-only pools"); comments restating the name of the
  function/variable/module ("Env configuration (D7)" above configModule); comments
  like "This is a singleton" above bind<T>() with singleton { }; comments explaining
  obvious Kotlin syntax; comments like "// add user to DB" before a function named
  addUserToDb()

## Functions

- Max 30 lines
- Max 4 parameters
- Single responsibility

## Tests

- Test names in backticks: ``fun `given... when... then...`() ``
- given-when-then structure
- One assert per test preferred

## Tools

- ktlint + detekt run automatically: `./gradlew ktlintCheck detekt` (verdict-only
  reading per T18); auto-fix with `./gradlew ktlintFormat`
